# SSH-Buddy v0.7.0 Release Notes

v0.7.0 folds the entire unreleased v0.6.1 candidate into a desktop-lifecycle, security, recovery, and launch-reliability release. It adds backend-owned login startup, minimized startup, tray close behavior, and single-instance restoration while retaining the candidate's SSH validation, SQLite recovery, AppImage, Konsole, diagnostics, CSP, and frontend work.

## Highlights

- Validate SSH host and username values before persistence, SSH config resolution/import, command display, and SSH, SFTP, `ssh-copy-id`, or tunnel launch.
- Reject unsafe SSH config aliases before passing them to `ssh -G`, and prevent rejected entries from creating key references or partial server records.
- Check SQLite integrity before and after migrations and create a uniquely named, recoverable backup before modifying an existing non-empty database with pending migrations.
- Keep login startup OS-owned and verified after every update; persist start-minimized and close-to-tray in SQLite with defaults off.
- Delay the initial window decision until database migration and settings loading finish, with normal recovery presentation after any data failure.
- Provide a mandatory tray Open/Quit menu, safe normal-close fallback, and second-instance window restoration.
- Keep the app open in a database-disabled state after a startup data error so the UI can explain that the existing database was not deleted.
- Restore host paths and libraries before detecting or launching external tools from an AppImage while retaining desktop-session and SSH-agent variables.
- Report terminal availability and resolved executable paths, and test the currently visible terminal selection without saving it first.
- Launch Konsole with `--separate --noclose -e`.
- Distinguish started, not found, pre-launch validation failure, spawn failure, and immediate exit outcomes. Immediate-exit stderr is control-character sanitized and capped at 2 KiB.
- Refine the selected-server layout, connection action cards, diagnostics disclosure, responsive stacking, and startup recovery message.

## Database Recovery Behavior

SSH-Buddy runs `PRAGMA quick_check(1)` before any migration and again after all migrations finish. When an existing non-empty database has pending file migrations, it first creates a sibling file named like:

```text
ssh-buddy.sqlite3.pre-migration-<timestamp>-<id>.bak
```

The backup is created through SQLite before schema modification starts. A backup failure stops migration. If database open, integrity, backup, or migration fails, database-backed commands remain unavailable for that session and the startup screen directs the user to preserve the original database and backups. SSH-Buddy does not delete or silently replace the existing database.

The regression fixture covers v0.6.0 saved servers, groups, tags, SSH key references, web links, tunnels, RDP settings, and application settings. A separate pending-migration test verifies that the backup is internally consistent and contains the pre-migration schema state.

## Desktop Behavior

- **Start SSH-Buddy when I sign in** uses the official Tauri autostart plugin. The operating-system registration is authoritative and is queried after every enable or disable attempt, including failures.
- **Start minimized** is stored in SQLite and applies to the next fresh process launch. It creates a minimized taskbar window rather than a tray-only launch.
- **Hide to system tray when closing** is stored in SQLite and applies immediately only when a tray is live. The required context menu always includes Open SSH-Buddy and Quit SSH-Buddy.
- Tray creation and persistence are ordered to avoid inconsistent state. Tray or window-hide failures permit normal close so the process is never stranded invisibly.
- The single-instance plugin is registered first. A second launch restores, shows, and focuses the existing main window.
- A database or initial settings-load failure overrides start-minimized and shows the recovery UI normally.

## Launch Outcomes

- Started: the selected local terminal remained running through the immediate-failure window, or its launcher exited successfully after handing off. This does not confirm an SSH or RDP connection.
- Not found: a required tool or selected terminal was unavailable, including a tool that disappeared between detection and launch.
- Pre-launch validation failed: saved input, a key path, or another launch prerequisite was invalid.
- Spawn failed: the operating system rejected the process start.
- Exited immediately: the launched terminal returned a nonzero status or signal during the bounded observation window. The diagnostic includes an exit code when available and sanitized, bounded stderr when present.

## Security Model

- SSH-Buddy continues to use backend-owned argv/process APIs without shell interpolation.
- Hosts may use safe aliases, IPv4, IPv6, bracketed IPv6, scoped IPv6, and supported OpenSSH destination characters. Option-like values, whitespace/control characters, and `@` in the separate host or username fields are rejected.
- SSH config import remains preview-first and read-only. Concrete aliases are validated before `ssh -G`; resolved destinations are validated again before preview selection and import.
- Production content and connectivity remain local except for required Tauri IPC. Development additionally allows the local Vite WebSocket.
- Clipboard capability remains write-only. Saved web links are opened only by the backend after `http://`/`https://` validation and embedded-credential rejection.
- SSH-Buddy does not store private key contents, passphrases, SSH/SFTP/RDP passwords, sudo passwords, or remote passwords.
- No signing credentials, notarization, password automation, embedded terminal, new protocol, or broad network scanning was added.

## Install Notes

Linux users should start with the AppImage:

```sh
chmod +x SSH-Buddy-v0.7.0-linux-amd64.AppImage
./SSH-Buddy-v0.7.0-linux-amd64.AppImage
```

On some Wayland/WebKitGTK sessions, use:

```sh
WEBKIT_DISABLE_DMABUF_RENDERER=1 ./SSH-Buddy-v0.7.0-linux-amd64.AppImage
```

SSH, SFTP, and public key install require the relevant OpenSSH clients in the host `PATH`: `ssh`, `sftp`, and `ssh-copy-id`. Launch actions and terminal testing require Konsole, kitty, Alacritty, WezTerm, GNOME Terminal, or xterm. RDP requires `xfreerdp3` or `xfreerdp`.

Before enabling login startup from an AppImage, move the AppImage to a stable path and keep it there. Moving or renaming it afterward can invalidate the OS registration.

Windows and macOS builds are unsigned. Windows SmartScreen, macOS Gatekeeper, browser download warnings, or manual trust steps may appear. Signing and notarization remain future work.

## Known Limitations

- Linux remains the primary development target.
- Windows and macOS artifacts remain experimental, require broader real-machine testing, and are unsigned.
- The bounded launch observation confirms only immediate local process behavior; later terminal, SSH, SFTP, RDP, tunnel, or `ssh-copy-id` failures remain visible in the external terminal.
- AppImage host-environment restoration depends on the runtime-provided original variables when present and otherwise filters paths under the AppImage mount.
- SSH config import handles concrete aliases only and does not edit `~/.ssh/config`.
- Reachability history remains in memory, ping may be blocked, and port scan remains selected-host-only with a fixed allowlist.
- No VNC, sync, KeePassXC integration, embedded terminal, embedded RDP/SFTP, background scanning, password vaulting, remote forwarding, or SOCKS forwarding is included.

## Release Procedure

1. Finish the release candidate on a review branch and run the complete verification checklist.
2. Publish the release branch and open a pull request against `main` when repository access is available.
3. Wait for required CI and review. Merge without rewriting shared history only when repository controls allow it.
4. Confirm version `0.7.0` in `package.json`, the root package entries in `package-lock.json`, `src-tauri/Cargo.toml`, only the `ssh-buddy` package entry in `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json`.
5. Create and push only `v0.7.0`; never create or publish v0.6.1.
6. Verify that the release workflow creates a draft prerelease containing the AppImage, NSIS installer, and both macOS DMGs.
7. Download the generated AppImage and run the mandatory CachyOS/KDE Wayland acceptance gate. Keep the release draft if the host is unavailable or any mandatory item fails.
8. After the AppImage passes and all expected artifacts are present, publish that existing draft as the single v0.7.0 prerelease.
